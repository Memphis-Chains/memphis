# Memphis refactor evidence audit

Baseline: local checkout `7c51f1a7`, package `1.13.5`, inspected on 2026-10-11 and 2026-10-12. The checkout contained existing staged changes and gained additional work during the session. These findings concern the inspected working tree and observed installation; they do not assert the state of upstream main or the completion of historical plans.

## User needs and evidence rules

The primary workflow is an Omarchy desktop operator using Memphis, MiniMax, native TUI, encrypted credentials and persistent memory. Repair must preserve existing data, support reboot and updates, and let the agent complete authorized work without inventing permission barriers. The later request adds a documented refactor program, including an assessment of the proposed vault probe.

Evidence labels: **observed** means a host check or execution produced the result; **code** means the cited implementation establishes the behavior; **reported** means the operator supplied the example; **hypothesis** requires a reproducer. A passing configuration check is not a successful provider request. A readable archive is not a successful restore.

## Assessment of the quoted proposal

The quoted JSON is a proposed response shape. Its `verified`, masked value, fingerprint and length are not measured properties of this host's key.

1. **Keep:** a diagnostic that can answer whether a configured credential is present, intact and locally decryptable without returning it.
2. **Change:** split credential verification from network authentication and generation verification. Reuse existing provider clients; MiniMax already has a connector in both runtimes.
3. **Change:** an allowlisted output schema and dedicated broker operations must protect the response. A generic callback is an internal convenience, not a security proof. A callback can also throw a secret-bearing error or pass data to a logger.
4. **Change:** audit through a versioned shared contract outside chains. Adding a second arbitrary `logs/vault-audit.jsonl` sink would create another lifecycle and permission policy to maintain.
5. **Change:** represent subject, surface, grant, capability and operation explicitly. Do not infer passphrase requirements from `tier=2`, or use the model's verbal assurance as authorization.
6. **Change:** quotas limit load and paid requests. They do not prevent extraction through an unsafe response. Use authenticated scopes and persisted counters only where required.
7. **Keep with correction:** generator and registry synchronization matters. The currently configured CI job catches drift; it is not a Rust compiler rule, and adding a native tool involves its advertised schema and dispatch plus the generator's explicit list, not merely three TS registration sites.

## Remaining warnings and scope

After S0, all required doctor checks passed. Its 14 warnings included the embedding and recovery false positives, optional HTTP MCP, voice engines, Brave key, multi-agent sync, external plugins, training checkpoints, demo readiness, remote-provider preference, RSS, alert transport, emergency log classification and a scheduler status inconsistency. Optional integrations stay optional. Do not delete `emergency.log`, initialize vault again, enable channels, or reset memory merely to obtain a warning-free report.

The audit does not establish the active age of historic secrets, explain the entire reported 105k-token prompt, prove remote provider availability beyond the observed request, or validate every uncommitted code change. It supplies regression targets for these uncertainties instead of treating them as completed repairs.
