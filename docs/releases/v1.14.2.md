# Memphis v1.14.2 — Release Notes

**Release date:** 2026-11-24
**Tag:** `v1.14.2`
**Since:** `v1.14.1`

One ledger entry closed: the package that ships. The published v1.14.1 tarball
installed cleanly and then could not start — and every gate said it was fine.

Every number below was measured on the operator's host, against the artefact
that was actually published.

---

## TL;DR

- **The published package now starts.** Measured against the v1.14.1 tarball
  in a clean prefix with npm 12.0.2: the install succeeded, and every command
  died with `Could not locate the bindings file` — because npm 12 blocks
  dependency install scripts by default and `better-sqlite3` ships no
  prebuilt binding.
- **The gate now looks at the thing that ships.** It installs under a declared
  policy, proves the native binding exists, and probes `memphis vault list
  --json` — a command that opens the journal database. The old probes
  (`--help`, `completion bash`) never touched it.
- **The CLI says what to do.** A missing binding prints the cause and the one
  line that fixes it, not thirteen candidate paths.
- **The operator is told the rule.** The README documents npm 12's install
  policy and why approving `onnxruntime-node` breaks the install.

---

## What broke, measured

Against the **published** `memphis-chains-memphis-1.14.1.tgz` (4 599 032 B,
checksum verified against the workflow's own `SHA256SUMS`), installed into a
clean prefix with npm 12.0.2:

| step | result |
| --- | --- |
| `npm install` | **exit 0** — the install succeeded |
| `memphis --version` | `[ERROR] Failed to load Memphis CLI: Could not locate the bindings file` + 13 candidate paths |
| `node_modules/better-sqlite3/build/` | **does not exist** — the native binding was never built |

The cause was npm's, not the package's:

- npm 12 **blocks dependency install scripts by default**;
- it reads `allowScripts` from the **project root** — the installed
  `node_modules/@memphis-chains/memphis/package.json` carried
  `{"better-sqlite3": true, "esbuild": true, "onnxruntime-node": true}` and
  the script was blocked anyway;
- `better-sqlite3` ships no prebuilt binary — its install script is what
  fetches one.

With one line in the consumer's project,
`{ "allowScripts": { "better-sqlite3": true } }`, the install builds the
binding and the CLI starts. Approving **more** breaks it: `onnxruntime-node`'s
script downloads `onnxruntime-linux-x64-gpu-1.21.0.tgz` and gets **404**,
aborting the whole install — the CPU runtime Memphis uses ships inside the
package, and the repository's own `.npmrc`
(`onnxruntime-node-install-cuda=skip`) is what keeps the repo's install alive.

## Why the gates missed it

`ops:release-preflight` passed 11/11 on this host, and the release workflow's
`test` job passed, on an artefact that cannot start:

- `scripts/validate-package-artifact.mts` installed with `--ignore-scripts` —
  which guarantees that no native binding is built;
- its two probes were `memphis --help` and `memphis completion bash` — neither
  opens the journal database, so neither can tell a working package from a
  dead one.

This is the second half of E-10: the `files` list was fixed; the proof that
the tarball **runs** was not.

## What changed

| piece | what it is |
| --- | --- |
| `scripts/validate-package-artifact.mts` | **the owner** — installs under a declared policy (`allowScripts: {better-sqlite3: true}`, `onnxruntime-node-install-cuda=skip`), asserts the native binding exists, probes `memphis vault list --json` |
| `bin/install-remedy.mjs` | the sentence the CLI prints when the binding is missing |
| `bin/memphis.js` | prints that sentence instead of leaving the operator with the raw loader error |
| `tests/ops/package-install-contract.test.ts` | the runner (6 assertions) |

**Falsifier, measured:** with the approval revoked in the install prefix, the
gate fails (exit 1) with `the installed package has no better-sqlite3 native
binding`. With it, the binding is there and the probe answers
`{"ok": true, "entries": []}`.

## Operator note (npm 12 and newer)

```json
{
  "allowScripts": { "better-sqlite3": true }
}
```

Add it to the project that installs Memphis, or run
`npm install-scripts approve better-sqlite3` there, then reinstall. Do not
approve `onnxruntime-node` — its install script downloads a CUDA build that
answers 404, and Memphis ships the CPU runtime inside the package.
